# 11 — P2P 評估與決定記錄

> **決定：商用 BGM 訂閱路線不採用 P2P。**
> 本文件記錄評估過程、拒絕的理由、以及**在什麼條件下應該重新討論**。
> 這個問題在專案初期被反覆提出，因此完整留存判斷依據，避免日後憑印象重新爭論。

---

## 1. 為什麼這個問題值得一份專門文件

P2P 在直覺上很有吸引力：「讓使用者貢獻頻寬，平台就不用付錢」。這個直覺在很多產品裡是對的，但**取決於三個前提**：

1. 頻寬確實是主要成本
2. peer 的品質足以支撐（線上時間、網路穩定度、意願）
3. 內容的散布不會損害其他更重要的能力

本專案在第 1 點就不成立，第 3 點則有致命衝突。以下逐項說明。

---

## 2. 前提檢驗

### 2.1 頻寬成本：**¥0**

架構選用 Cloudflare R2，**出口流量免費**（見 [02-architecture](02-architecture.md#5-成本模型概估)）。這不是「便宜」，是零，且不隨規模改變。

| 規模 | 月間出口流量 | R2 出口費 |
|---|---|---|
| 500 店 | 約 17 TB | **$0** |
| 5,000 店 | 約 170 TB | **$0** |
| 50,000 店 | 約 1.7 PB | **$0** |

P2P 的價值是削減頻寬支出。**60% 的卸載率乘以 $0 仍然是 $0。**

> 對照：若改用 AWS CloudFront，500 店約需每月 $1,400，屆時 P2P 才開始有經濟意義。這也是下方「重啟條件」的第一項。

### 2.2 peer 品質：**這一點 P2P 是有利的**

必須誠實記錄：**商用播放器是接近理想的 peer**，與一般消費者裝置完全不同。

| 條件 | 手機（初期評估的前提） | 商用播放器（實際架構） |
|---|---|---|
| 電源 | 電池，耗電敏感 | 常時通電 |
| 線上時間 | 斷續 | 每日 10 時間以上、常時起動 |
| 背景動作 | iOS Safari は WebRTC が停止 | 前景服務、開機自啟 |
| 網路 | 行動網路（従量制） | 固定 Wi-Fi／有線 |
| 本地快取 | ほぼ無し | **24 時間分を既に保持** |
| 内容の重複度 | 長尾・ランダムアクセス | **情境ベースで高い重複** |

情境播放（scene engine）使得同業種・同時間帯の店舗が同じ曲群を再生するため、swarm 効率は点播音楽より遥かに高い。**技術的な実現可能性そのものは高い。**

拒絕的理由不在技術，在下面兩點。

### 2.3 內容散布的代價：**與撤銷能力直接衝突**

產品的核心價值是**「可以證明並控制播放了什麼」**（見 [04-rights-chain](04-rights-chain.md)）。撤銷流程的設計目標是：

- 緊急推播到達裝置 **< 5 分鐘**
- 離線裝置最長 **6 小時**（下次同步）
- 離線容許上限 **7 日**，逾期停播

P2P 會把曲目副本散布到數百台不完全受控的裝置。發生污染事件時：

- 從 R2 刪除檔案 → 快速且可證明
- **從 peer 快取中完全清除 → 無法保證**

「無法有效移除侵權內容」一旦成立，會直接侵蝕管理外証明書的可信度，並削弱 DMCA 型安全港的抗辯基礎（Grokster 判例的核心爭點正是此處）。

**為了節省 $0 而動搖整個產品的法律基礎，是不成比例的交換。**

## 3. B2B 特有的否決理由

這一點在消費者產品中不存在，是本專案的決定性因素。

**P2P 意味著 A 店的裝置連線到 B 店的裝置。**

| 問題 | 說明 |
|---|---|
| **佔用客戶的營業網路** | 店內網路同時承載 POS 收銀、訂位系統、外送平台端末。BGM 裝置佔用上行頻寬 → 結帳延遲 → 客訴 |
| **跨客戶的 IP 曝露** | 兩家店的裝置互相看得見 IP。連鎖與企業客戶的資安審查無法通過 |
| **防火牆與 NAT** | 商業設施・百貨櫃位的企業網路多半封鎖 P2P，穿透失敗率高 |
| **歸因困難** | 音樂中斷時難以自證「不是 P2P 造成的」。B2B 客戶對此零容忍 |
| **銷售阻力** | 「這台機器也會上傳資料給其他店家」在合約說明階段就會被拒絕 |

消費者產品可以訴求「一起分享頻寬」。**B2B 客戶買的是「不要出事」，不是「一起貢獻」。**

## 4. 三種情境的分別評估

P2P 不是一個是非題。分開評估後結論不同：

| # | 情境 | 適合度 | 決定 |
|---|---|---|---|
| A | **商用串流的頻寬卸載** | ❌ 低 | **不做**。成本效益為零，且與撤銷能力衝突 |
| B | **連鎖店內部的快取共享** | ✅ 高 | **Phase 3 候補**。見下節 |
| C | **聽眾端電台模式** | 🟡 中 | 保留。價值在敘事而非成本 |

### 4.1 情境 B：連鎖店內部快取共享（唯一推薦者）

> **採用決定。** 完整規格見 [12-chain-cache-sharing](12-chain-cache-sharing.md)。

**限定同一法人旗下的裝置之間互相補充快取。** 20 家分店的播放器在開店前互相同步，僅第一台從 CDN 取得。

為什麼本情境的否決理由全部消失：

| 一般 P2P 的問題 | 連鎖內部的情況 |
|---|---|
| 跨客戶同意問題 | 同一法人自有裝置、自有網路 → **不存在** |
| IP 曝露 | 同一企業內部 → **不存在** |
| 撤銷不可控 | 裝置清單已知且完全受管 → **可逐台確認清除** |
| 銷售阻力 | 反而是賣點：「不佔用貴社總部的對外頻寬」 |

**且連鎖店是單價最高的客群。** 本情境的價值不在成本削減，在**連鎖客戶的銷售訴求**。

實作前提：

- 預設關閉，以組織單位明示同意後啟用
- 僅用於**開店前的快取預取**，絕不用於播放中的即時傳輸
- 撤銷推播仍走中央通道，不經 peer
- 同一 `organizations.id` 之內才建立連線

### 4.2 情境 C：聽眾端電台模式

若免費聽眾端提供「所有人同時收聽同一頻道」的電台，即具備直播特性（大量聽眾、同一內容、時間對齊），卸載率可達 60% 以上。

但頻寬成本仍為 $0，因此**本情境的價值是敘事性的**（「這個平台由社群共同支撐」），不是財務性的。若採用，應明確歸類為品牌投資而非成本優化，並列入該項的預算評估。

## 5. 重啟討論的條件

以下任一條件成立時，**應重新評估對應情境**，而非憑印象重啟全面討論：

| # | 觸發條件 | 重啟的情境 |
|---|---|---|
| 1 | 儲存／CDN 供應商變更，出口流量**不再免費**，且月額超過 **US$500** | A |
| 2 | 連鎖客戶（20 店以上）佔營收 **30% 以上**，且已收到「佔用總部對外頻寬」的實際反饋 | B |
| 3 | 聽眾端單一頻道的同時連線數超過 **5,000** | C |
| 4 | 商用播放器的快取預取造成店舖開店前的頻寬尖峰投訴 | B |

**條件 1 是唯一能讓情境 A 復活的因素。** 只要 R2 的出口免費政策維持，商用串流的 P2P 就沒有經濟基礎。

## 6. 產品身分的界線

評估過程中浮現一個更根本的問題，一併記錄：

「P2P 音樂分享網路」與「商用 BGM 訂閱服務」**是兩個不同的產品，不是同一產品的兩個功能**。

| | 商用 BGM 訂閱（本專案） | P2P 音樂分享網路 |
|---|---|---|
| 客戶 | 日本の店舗 | 全球創作者與聽眾 |
| 收入 | B2B 訂閱 | 幾乎無 |
| 核心能力 | **法律可信度・可控性** | **去中心化・抗審查** |
| 中心化 | 資產 | 原罪 |
| P2P | 累贅 | 產品本身 |

兩者的核心能力互為反面：中心化的可控性是 BGM 生意的護城河，卻是 P2P 網路要消滅的東西。

**本專案選擇商用 BGM 訂閱路線。** 若日後要做 P2P 分享網路，應作為獨立專案規劃，不併入本產品。
