# 05 — 管理外証明書與再生ログ

這兩者是店家實際購買的東西。音樂是體驗，**這兩份文件是產品**。

---

## 第一部分：管理外証明書

### 1. 用途

日本店家最常面對的情境是：有人上門詢問「這裡播的音樂處理過著作權了嗎？」。此時店家需要能立刻拿出來的東西。

実務上，**店頭掲示物的嚇阻效果最強** —— 多數詢問在看到貼紙的當下即結束。証明書 PDF 是第二層，再生ログ 是第三層（真正進入爭議時才需要）。

### 2. 三層防禦

| 層級 | 形式 | 使用時機 |
|---|---|---|
| 1 | **店頭掲示物**（貼紙／立牌 + QR） | 日常，被動嚇阻 |
| 2 | **管理外証明書 PDF** | 被詢問時出示 |
| 3 | **再生ログ 匯出** | 正式爭議、書面回覆時 |

### 3. 証明書內容

```
┌──────────────────────────────────────────────┐
│  楽曲管理団体 非管理 証明書                    │
│  Certificate of Non-Managed Repertoire        │
│                                               │
│  証明書番号   KND-2026-000123                  │
│  発行日       2026年9月1日                     │
│  有効期間     2026年9月1日 〜 2027年8月31日     │
│                                               │
│  契約者       株式会社◯◯                       │
│  対象施設     ◯◯カフェ 渋谷店                  │
│  施設住所     東京都渋谷区…                     │
│                                               │
│  ── 証明内容 ──────────────────────────       │
│  本サービスが上記施設に配信する楽曲は、         │
│  すべてオリジナル楽曲であり、一般社団法人       │
│  日本音楽著作権協会（JASRAC）および            │
│  株式会社NexTone の管理楽曲に該当しません。     │
│                                               │
│  配信元は各楽曲について、権利者本人から         │
│  再許諾可能な公衆送信・演奏に関する許諾を       │
│  得ています。                                  │
│                                               │
│  ── 対象カタログ ──────────────────────       │
│  カタログ基準日   2026年9月1日                 │
│  収録楽曲数       12,847 曲                    │
│  カタログ検証値   sha256:a3f2…（Merkle root）  │
│                                               │
│  ── 検証 ────────────────────────────         │
│  この証明書の有効性は下記で確認できます        │
│  https://kanade.example/verify/KND-2026-000123 │
│  [QR コード]                                   │
│                                               │
│  発行者  ◯◯株式会社                            │
│  署名    [デジタル署名]                        │
└──────────────────────────────────────────────┘
```

**注意事項：**

- **不得記載「JASRAC への支払いが不要」** —— 只陳述「不屬於管理曲目」這個事實
- 有效期間與訂閱期間連動；訂閱終止時証明書自動失效
- **不承諾曲庫永不變動**，而是綁定**カタログ基準日**與 Merkle root

### 4. Merkle root 的作用

証明書綁定發行當日的曲庫快照（`catalog_snapshots.merkle_root`）。

建構方式：取快照當下所有 `commercial_catalog_entries` 的 `audio_sha256`，**依位元組序排序**後建構 Merkle tree。

用途：對**單一曲目**出具 Merkle proof，證明「該曲於某快照時點確實在已審核曲庫中」，且**無須揭露完整曲庫**。當爭議聚焦於某一首歌時，這是強而有力且可獨立驗證的證據。

> 實作優先度：Phase 3。Phase 2 先用 `catalog_snapshot_id` 引用即可，Merkle root 欄位先填全曲庫雜湊的簡單串接雜湊。

### 5. 公開驗證頁

`GET /verify/{cert_no}` —— 無需登入，任何人可存取。

顯示：

| 欄位 | 說明 |
|---|---|
| 狀態 | 有効 / 期限切れ / **失効** |
| 契約者名、施設名 | — |
| 有効期間 | — |
| カタログ基準日、収録曲数 | — |
| 発行者情報 | — |

**不顯示**：訂閱金額、聯絡資訊、店家內部識別碼。

`verify_token` 用於防止以連號猜測列舉他人証明書；URL 中同時包含 `cert_no`（可讀）與 token（`?t=`）。QR code 內含完整 URL。

### 6. 発行與失効

| 事件 | 動作 |
|---|---|
| 訂閱開始（Standard 以上） | 自動發行，寄送 PDF + 掲示物列印檔 |
| 訂閱更新 | 發行新証明書，舊証明書於期滿後自然失效 |
| 訂閱取消 | 於期末失效（`valid_to` 不變更） |
| 欠費 | 寬限 14 日；逾期則 `revoked_at` 設定 |
| **平台側曲庫污染事件** | 不撤銷証明書 —— 証明書綁定的是快照，撤銷會讓店家失去當時合法播放的證據 |

> 最後一項容易搞錯。發生污染時該做的是**主動通知並承擔責任**（見 [04 第 4 節](04-rights-chain.md#4-撤銷revocation)），不是撤銷店家的証明書。撤銷等於把責任推給客戶。

## 第二部分：再生ログ

### 7. 為什麼是必要功能

若レコード演奏・伝達権 的指定團體採概括徵收，舉證責任可能落在店家身上。此時店家需要的是：**「本店於某期間播放的每一首曲目及其權利狀態」的完整記錄。**

這也是現有 BGM 服務普遍缺乏的功能 —— 是明確的差異化點。

### 8. 事件模型

播放器對**每一次播放**產生一筆事件：

```json
{
  "client_event_id": "018f2c1a-...",
  "device_id": "018f2b90-...",
  "venue_id": "018f2b8f-...",
  "track_version_id": "018f2c00-...",
  "audio_sha256": "a3f2b1...",
  "scene_id": "018f2c05-...",
  "started_at": "2026-09-01T14:23:07+09:00",
  "played_ms": 187430,
  "completed": true
}
```

**規則：**

- `client_event_id` 由裝置產生（UUIDv4），作為**冪等鍵**。離線期間累積、恢復連線後重送，重複送出不會產生重複記錄。
- `played_ms` 記錄**實際播放時長**而非曲目長度。跳過、關店中斷都要如實反映 —— 這同時是分潤的計算基礎。
- 裝置本地保留最近 **30 日** 事件，防止長時間離線後遺失。
- 上傳批次上限 500 筆，失敗以指數退避重試。

### 9. 匯出格式

店家可自助匯出任意期間：

**CSV**（供試算表分析）

```csv
再生日時,楽曲ID,楽曲名,アーティスト,再生秒数,権利ステータス,証明書番号
2026-09-01 14:23:07,KND-T-0012847,朝の光,Yuki Aoi,187,管理外,KND-2026-000123
```

**PDF 報告書**（供正式提出）

- 封面：施設名、対象期間、証明書番号、発行日
- 統計：総再生曲数、ユニーク楽曲数、総再生時間
- **権利ステータス別集計 —— 「管理外 100%」是這份報告的重點結論**
- 明細（可選附錄）
- 頁尾：発行者、デジタル署名、検証 URL

### 10. 保存與不可變性

| 項目 | 規格 |
|---|---|
| 保存期限 | **5 年** |
| 儲存 | Postgres 月分區表 → Phase 3 遷 ClickHouse |
| 不可變性 | 寫入角色僅有 INSERT + SELECT，`REVOKE UPDATE, DELETE` |
| 備份 | 每日增量，異地保存 |
| 店家刪除帳號時 | **記錄保留至法定期限屆滿**，條款中明示 |

最後一項須在店家條款中明確告知：這是為了保護店家自身在爭議中的舉證能力，不是平台單方面留存資料。若允許刪除，記錄的證據價值即失效 —— 因為可被主張是選擇性保留。

### 11. 資料量估算

500 店 × 每日 10 小時 × 約 20 曲/小時 = **每日約 10 萬筆**，年約 3,650 萬筆。

Postgres 月分區表足以支撐至約 2,000 店規模。超過後遷移至 ClickHouse，分區鍵維持 `started_at`，遷移可透過雙寫平滑進行。
